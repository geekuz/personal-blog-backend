# Spring Boot Backend Handoff

## 1. Purpose

Build a Spring Boot REST API for the existing React personal blog. The frontend
currently reads Markdown files from `src/posts/`; it will be migrated to read
published posts and tags from this API.

The first backend release should support the public blog without requiring user
accounts. Author authentication and post management are a separate second phase.

## 2. Recommended stack

- Java 21+
- Spring Boot 3.x
- Spring Web
- Spring Data JPA
- Bean Validation
- PostgreSQL
- Flyway for database migrations
- springdoc-openapi for Swagger/OpenAPI
- JUnit 5, MockMvc, and Testcontainers
- Spring Security only when admin endpoints are introduced

Use UTC for stored timestamps and return timestamps in ISO 8601 format.

## 3. Domain model

### Post

| Field | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Generated by backend |
| `slug` | string | Required, unique, lowercase kebab-case, max 160 |
| `title` | string | Required, 1–200 characters |
| `summary` | string | Required, 1–500 characters |
| `content` | string | Required Markdown source |
| `tags` | tag collection | Zero or more unique tags |
| `status` | enum | `DRAFT` or `PUBLISHED` |
| `publishedAt` | timestamp/null | Required when published |
| `createdAt` | timestamp | Set by backend |
| `updatedAt` | timestamp | Set by backend |

### Tag

| Field | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Generated by backend |
| `name` | string | Required, unique normalized value, max 50 |
| `slug` | string | Required, unique, lowercase kebab-case |

A post can have many tags and a tag can belong to many posts. Tag matching and
uniqueness should be case-insensitive.

## 4. Public API contract (MVP)

Base path: `/api/v1`

All successful and error responses use `application/json; charset=utf-8`.

### `GET /posts`

Returns published posts only, newest first.

Query parameters:

| Parameter | Default | Notes |
| --- | --- | --- |
| `page` | `0` | Zero-based, minimum 0 |
| `size` | `10` | 1–50 |
| `q` | omitted | Case-insensitive title/summary search |
| `tag` | omitted | Exact normalized tag slug |

Example: `GET /api/v1/posts?page=0&size=10&q=react&tag=learning`

Response:

```json
{
  "items": [
    {
      "slug": "why-i-chose-react",
      "title": "Why I Chose React to Learn First",
      "summary": "A quick take on why React is a solid first framework.",
      "tags": ["react", "learning"],
      "publishedAt": "2026-06-18T09:00:00Z",
      "readingTimeMinutes": 3
    }
  ],
  "page": 0,
  "size": 10,
  "totalItems": 1,
  "totalPages": 1,
  "hasNext": false
}
```

Do not return full Markdown content in list results. `readingTimeMinutes` should
be calculated by the backend using a documented, consistent algorithm (initially
`max(1, round(wordCount / 200))`).

### `GET /posts/{slug}`

Returns one published post.

```json
{
  "slug": "why-i-chose-react",
  "title": "Why I Chose React to Learn First",
  "summary": "A quick take on why React is a solid first framework.",
  "content": "## The whole model is small\n\nMost of React...",
  "tags": ["react", "learning"],
  "publishedAt": "2026-06-18T09:00:00Z",
  "updatedAt": "2026-06-18T09:00:00Z",
  "readingTimeMinutes": 3
}
```

Return `404` when the slug does not exist or belongs to a draft. Public callers
must not be able to infer that a draft exists.

The post-detail DTO may later add lightweight navigation relationships without
embedding complete posts:

```json
{
  "previousPost": { "slug": "older-post", "title": "Older post" },
  "nextPost": { "slug": "newer-post", "title": "Newer post" },
  "relatedPosts": [
    { "slug": "related-post", "title": "Related post", "summary": "..." }
  ]
}
```

If implemented, derive previous/next links from the same deterministic public
ordering as the post list. Related-post selection must include published posts
only and should be deterministic (for example shared tags, then publication
date). Keep the fields absent until their behavior is implemented and tested.

### `GET /tags`

Returns tags used by at least one published post.

```json
{
  "items": [
    { "name": "React", "slug": "react", "postCount": 2 },
    { "name": "Learning", "slug": "learning", "postCount": 1 }
  ]
}
```

Sort tags alphabetically by name.

### `GET /health`

Optional application health response for hosting checks. Spring Boot Actuator's
standard health endpoint is also acceptable if it exposes no sensitive details.

## 5. Error contract

Use one shape for validation, not-found, conflict, and unexpected errors.

```json
{
  "timestamp": "2026-08-12T11:30:00Z",
  "status": 400,
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "path": "/api/v1/posts",
  "fieldErrors": {
    "size": "must be between 1 and 50"
  },
  "traceId": "optional-correlation-id"
}
```

Expected codes include `VALIDATION_ERROR`, `POST_NOT_FOUND`, `SLUG_CONFLICT`,
`UNAUTHORIZED`, `FORBIDDEN`, and `INTERNAL_ERROR`. Never return stack traces,
SQL errors, entity internals, or secrets to clients.

## 6. Admin API (phase 2)

Place protected endpoints under `/api/v1/admin`:

- `POST /posts` — create draft
- `PUT /posts/{id}` — replace editable post data
- `PATCH /posts/{id}/status` — publish or unpublish
- `DELETE /posts/{id}` — preferably soft-delete
- `GET /posts` — list drafts and published posts
- `GET /posts/{id}` — retrieve a post by internal ID

Use Spring Security. For a single-author blog, either an external identity
provider with JWT validation or a secure server-side session is preferred over a
custom authentication implementation. Decide the authentication mechanism before
finalizing admin request/response contracts.

Admin write DTO example:

```json
{
  "slug": "spring-boot-notes",
  "title": "Spring Boot Notes",
  "summary": "What I learned while building the blog API.",
  "content": "# Introduction\n\n...",
  "tags": ["spring-boot", "java"]
}
```

Use optimistic locking (for example a JPA `@Version` field) or an equivalent
mechanism to prevent one edit from silently overwriting another.

If image uploads are selected, add a dedicated protected media endpoint rather
than accepting arbitrary server filesystem paths. Validate authenticated author,
MIME type, decoded file type, size, and dimensions; generate collision-resistant
object keys; and return a public URL plus width, height, alt text, and optional
caption metadata. Prefer object storage with restricted write access. If uploads
are out of scope, allow only explicitly validated HTTPS image URLs in content.

## 7. Database and migration requirements

Create Flyway migrations for at least:

- `posts`
- `tags`
- `post_tags`
- relevant unique constraints and query indexes

Recommended indexes:

- unique `posts.slug`
- `(posts.status, posts.published_at desc)`
- unique normalized `tags.slug`
- foreign-key indexes on `post_tags`

Do not rely on Hibernate `ddl-auto=update` in production. Use migrations and set
schema validation in production.

Import the three existing Markdown files as seed data or provide an idempotent
one-time importer. Preserve their slugs, titles, summaries, dates, tags, and
Markdown bodies.

## 8. CORS and configuration

Allow only configured frontend origins, for example:

```text
http://localhost:5173
https://the-production-blog-domain.example
```

Do not use wildcard origins with credentialed requests. Store database URLs,
credentials, allowed origins, and signing configuration in environment variables
or a secret manager. Provide `application-local.yml` examples without secrets.

The frontend will use:

```text
VITE_API_BASE_URL=http://localhost:8080/api/v1
```

## 9. Behavioral requirements

- Public endpoints expose published content only.
- Post ordering is deterministic: `publishedAt DESC`, then `id DESC`.
- Slugs remain stable after publication unless explicitly edited by the author.
- Search and tag filters can be combined.
- Empty list results return `200` with `items: []`, not `404`.
- Unknown resources return the standard error shape.
- API DTOs are separate from persistence entities.
- Controllers remain thin; business rules belong in services.
- Markdown is stored as source. The current frontend renders it safely without
  raw HTML; the backend must not enable unsafe HTML as part of processing.

## 10. Testing and delivery acceptance criteria

The backend is ready for frontend integration when:

- PostgreSQL starts locally through documented Docker Compose or equivalent.
- Flyway creates a clean database from zero.
- The three existing posts can be retrieved through the public API.
- Pagination, combined search/tag filters, sorting, and 404 behavior are tested.
- Drafts never appear through public endpoints.
- Constraint and validation failures use the documented error contract.
- CORS works for the Vite development origin.
- Integration tests run against PostgreSQL via Testcontainers.
- `./mvnw test` (or `./gradlew test`) passes from a clean checkout.
- Swagger/OpenAPI documents the final contract.
- A README explains setup, configuration, tests, migrations, and production run.

## 11. Decisions to confirm before phase 2

- Maven or Gradle
- Hosting provider and PostgreSQL provider
- Admin authentication method
- Whether post images are external URLs or uploaded files
- Whether scheduled publishing is required
- Whether comments, reactions, view counts, or subscribers are in scope
- Whether previous/next and related-post relationships are computed by the
  backend or derived from paginated frontend data

These features should not delay the public read-only MVP.
